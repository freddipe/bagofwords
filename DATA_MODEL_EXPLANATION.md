# What is `data_model` in the Coder Prompt?

**Location**: Passed to `Coder.data_model_to_code()` in `backend/app/ai/agents/coder/coder.py:21`

The `data_model` is a **structured specification** that describes what data to fetch and how to format it for visualization. It's like a blueprint that the Coder uses to generate the correct Python/SQL code.

---

## Overview

The `data_model` is a JSON object generated by the **Planner/LLM** that tells the Coder:

1. **What type of visualization** to create (bar chart, table, etc.)
2. **Which columns** to fetch (with their sources)
3. **How to map data** to chart elements (series configuration)
4. **Optional transformations** (grouping, sorting, filtering)

---

## Components Explained

### 1. Type - Visualization Type

```python
"type": "bar_chart"
```

**Possible Values:**
- `"table"` - Tabular data display
- `"bar_chart"` - Bar chart
- `"line_chart"` - Line chart
- `"pie_chart"` - Pie chart
- `"area_chart"` - Area chart
- `"scatter_plot"` - Scatter plot
- `"heatmap"` - 2D heatmap
- `"candlestick"` - Financial OHLC chart
- `"treemap"` - Hierarchical treemap
- `"radar_chart"` - Multi-dimensional radar
- `"map"` - Geographic map
- `"count"` - Single KPI value

**Purpose**: Tells the Coder what kind of output DataFrame structure to create.

## Complete Example: Bar Chart

### User Request
"Show revenue by region as a bar chart"

### Generated Data Model

```json
{
  "type": "bar_chart",
  "columns": [
    {
      "generated_column_name": "region",
      "source": "sales.region",
      "description": "Sales region identifier.",
      "source_data_source_id": "uuid-123"
    },
    {
      "generated_column_name": "revenue",
      "source": "SUM(sales.amount)",
      "description": "Total revenue amount.",
      "source_data_source_id": "uuid-123"
    }
  ],
  "series": [
    {
      "name": "Revenue",
      "key": "region",
      "value": "revenue"
    }
  ],
  "group_by": ["region"],
  "limit": 100
}
```

### How Coder Interprets This

**1. Type = "bar_chart"**
→ Create a DataFrame suitable for bar chart rendering

**2. Columns**
→ Need to fetch `region` and `revenue` from `sales` table
→ `revenue` is an aggregation: `SUM(sales.amount)`

**3. Series**
→ Map `region` to X-axis (categories)
→ Map `revenue` to Y-axis (values)
→ Label as "Revenue"

**4. Group By**
→ Add `GROUP BY region` to SQL

**5. Limit**
→ Add `LIMIT 100` to SQL

### Generated Code

```python
def generate_df(ds_clients, excel_files):
    import pandas as pd

    df = ds_clients['Sales DB'].execute_query("""
        SELECT
            region,
            SUM(amount) as revenue
        FROM sales
        GROUP BY region
        ORDER BY revenue DESC
        LIMIT 100
    """)

    print("df Info:", df.info())
    print("df head:", df.head())
    print("Final df Preview:", df.head())

    return df
```

**Resulting DataFrame**:
```
     region  revenue
0     North   150000
1     East    180000
2     South   120000
3     West     95000
```

This DataFrame structure matches the `data_model` specification:
- ✅ Has `region` column (from columns[0])
- ✅ Has `revenue` column (from columns[1])
- ✅ Grouped by `region` (from group_by)
- ✅ Limited to 100 rows (from limit)

## How Data Model is Generated

### Phase 1: LLM Generates Data Model

**Location**: `backend/app/ai/tools/implementations/create_widget.py:159`

The LLM receives a prompt like:

```
User wants: "Show revenue by region as a bar chart"

Available schemas:
<schemas>
  <data_source id="uuid-123" name="Sales DB">
    <table name="sales">
      <column name="region" dtype="VARCHAR"/>
      <column name="amount" dtype="DECIMAL"/>
    </table>
  </data_source>
</schemas>

Generate a data model (JSON) with:
- type: chart type
- columns: which columns to use (with source_data_source_id)
- series: how to map columns to chart
- group_by: aggregation fields
```

### Phase 2: Streaming Parsing

```python
parser = JSONParser()
current_data_model = {
    "type": None,
    "columns": [],
    "series": [],
    "group_by": [],
    "limit": None
}

async for chunk in llm.inference_stream(prompt):
    buffer += chunk
    parsed = parser.parse(buffer)  # Incremental JSON parsing

    if "type" in parsed:
        current_data_model["type"] = parsed["type"]
        yield ToolProgressEvent(stage="data_model_type_determined")

    if "columns" in parsed:
        for column in parsed["columns"]:
            # Validate with DataModelColumn schema
            if is_complete(column):
                current_data_model["columns"].append(column)
                yield ToolProgressEvent(stage="column_added", column=column)

    if "series" in parsed:
        current_data_model["series"] = parsed["series"]
        yield ToolProgressEvent(stage="series_configured")
```

### Phase 3: Pass to Coder

```python
coder = Coder(model=..., organization_settings=...)

code = await coder.data_model_to_code(
    data_model=final_data_model,  # ← The complete data model
    prompt=user_prompt,
    schemas=schemas,
    ds_clients=ds_clients,
    excel_files=excel_files,
    ...
)
```

## Why Data Model is Important

### 1. **Separation of Concerns**
- **Planner**: Decides WHAT data is needed (data model)
- **Coder**: Decides HOW to get it (code)

### 2. **Type Safety**
Validated with Pydantic schemas:
- Ensures all required fields present
- Validates data types
- Provides clear structure

### 3. **Lineage Tracking**
`source_data_source_id` tracks which data source each column comes from:
- Enables impact analysis
- Powers data lineage visualization
- Supports access control

### 4. **Frontend Rendering**
The same data model is used by the frontend to:
- Determine which chart component to use
- Map DataFrame columns to visual elements
- Configure chart options

### 5. **Error Recovery**
If code generation fails, data model is preserved:
- Can retry with same data model
- Can modify data model
- Can analyze what went wrong

## Data Model Lifecycle

```
1. User: "Show revenue by region"
        ↓
2. Planner/LLM: Analyze schemas, generate data_model
        ↓
3. CreateWidgetTool: Validate and parse data_model
        ↓
4. Coder: Receive data_model in prompt
        ↓
5. Coder: Generate Python code based on data_model
        ↓
6. Executor: Run code, produce DataFrame
        ↓
7. Frontend: Use data_model to render DataFrame as chart
        ↓
8. Database: Store data_model with widget for future reference
```

---

## Key Takeaways

1. **Data Model = Blueprint**: Describes what data to fetch and how to structure it
2. **Generated by LLM**: Created by analyzing user intent and available schemas
3. **Validated Structure**: Uses Pydantic models for type safety
4. **Passed to Coder**: Included in Coder's prompt as context
5. **Used by Frontend**: Guides visualization rendering
6. **Lineage Tracking**: Tracks data source origins
7. **Separation of Concerns**: Decouples data specification from code generation

The data model is the **contract** between the Planner (what to get) and the Coder (how to get it), ensuring consistent, traceable, and type-safe data transformations!
